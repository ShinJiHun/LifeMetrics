# LifeMetrics 문서 스킬

LifeMetrics의 기획서·결과서를 저장소 안 마크다운으로 관리한다. 앱의 `/docs` 페이지(관리자 전용)가 이 파일들을 그대로 보여준다.
문서는 신지훈 본인 정리용이면서 포트폴리오로도 쓴다. 독자는 "이 사람이 무엇을 왜 만들었고 어떻게 풀었는지" 알고 싶은 사람이다.

## 파일

| 파일 | 내용 | 갱신 방식 |
| --- | --- | --- |
| `docs/plan.md` | 기획서: 목적, 사용자, 기능 범위, 구조, 로드맵 | 방향이 바뀔 때만. 로드맵 상태는 정리할 때마다 |
| `docs/report.md` | 결과서: 구현한 것, 수치, 기술 과제와 해결, 일정, 남은 과제 | 정리할 때마다 |
| `docs/history/YYYY-MM-DD.md` | 날짜별 작업 기록(중간 저장) | 기록 요청마다 새 파일 또는 같은 날 파일에 추가 |
| `docs/history/_last-sync.md` | 마지막 일괄 정리 시점(날짜, master 커밋) | 일괄 정리 끝에 갱신 |

원본 자료(맥에서 올린 pptx/pdf 등)는 NAS `/mnt/200gb/NAS/project-docs/lifemetrics/inbox/` 에 있다. 저장소에 복사하지 말고 읽어서 근거로만 쓴다.

## 요청별 절차

### 1. "오늘 한 거 기록해줘" (중간 저장)
1. `git log --all --no-merges --since=<오늘 00:00> --format='%ad %h %D | %s' --date=short` 로 오늘 커밋을 모은다(모든 브랜치).
2. 대화에서 사용자가 말한 내용이 있으면 함께 넣는다.
3. `docs/history/<오늘>.md` 에 아래 형식으로 쓴다(있으면 이어 쓴다).
   ```
   # 2026-11-18 작업 기록
   ## 한 일
   - [브랜치] 한 줄 요약 (커밋 abc1234)
   ## 결정·배운 점
   - ...
   ## 다음에 할 일
   - ...
   ```
4. plan.md/report.md 는 건드리지 않는다.

### 2. "문서 정리해줘" / "일괄 정리" (결과서 갱신)
1. `docs/history/_last-sync.md` 에서 마지막 정리 커밋을 읽는다.
2. 그 이후 근거를 모은다:
   - `git log <마지막커밋>..master --no-merges` (운영 반영분)
   - `git log --all --no-merges --since=<마지막날짜>` 중 master 에 없는 브랜치 (진행 중)
   - `docs/history/` 의 그 이후 파일
   - 운영 배포 정보: `/mnt/200gb/apps/static/deploy.json`
3. report.md 에서 바뀐 섹션만 고친다: 수치 표, 구현 기능 표, 일정 표(맨 위에 새 행), 진행 중, 남은 과제.
4. plan.md 의 로드맵 상태(완료/진행/예정)를 맞춘다.
5. 두 문서 맨 위 `> 기준:` 줄의 날짜와 커밋을 갱신하고, `_last-sync.md` 를 갱신한다.

### 3. 특정 수정 ("결과서에 따릉이 내용 추가", "기획서 목표 바꿔줘")
요청한 부분만 고친다. 다른 문장은 그대로 둔다. `> 기준:` 줄은 바꾸지 않는다(일괄 정리가 아니므로).

## 작성 규칙

- 한국어, 평서문(~합니다). 문장은 짧게. 첫 문장이 그 섹션의 결론.
- 수치는 근거가 있는 것만 쓴다(git, DB 카운트, 화면에서 확인한 값). 추측한 숫자는 쓰지 않는다. 모르면 `확인 필요:` 한 줄로 남긴다.
- 운영에 반영된 것(master)과 브랜치에만 있는 것을 구분한다. 브랜치 것은 "진행 중"에만 쓴다.
- 용어는 앱 화면과 같게: "애슐리트 페르소나", "랜도너스", "따릉이", "개발 요청함".
- 표는 GitHub 마크다운 표. 일정 표는 최신이 위.
- 포트폴리오로 공개될 수 있으므로 **쓰지 않는 것**: 서버 IP, 토큰·비밀번호·키 파일 이름, DB 계정명, 개인 의료 기록의 구체 내용(병명·수치), 다른 사람 실명. 기능 설명은 "진단서 업로드로 치료 기록 채우기"처럼 기능 수준까지만.
- 결과서의 "기술 과제와 해결"은 포트폴리오의 핵심이다. 문제 → 선택지 → 결정 → 결과 순서로 짧게 쓴다.

## 뷰어

- `frontend/src/pages/DocsPage.tsx` 가 `docs/*.md` 와 `docs/history/*.md` 를 빌드 시 번들한다. 문서를 고치면 프론트를 다시 빌드·배포해야 화면에 반영된다(개발 요청함 워커가 dev 배포까지 해준다).
- 새 문서를 추가하면 `DocsPage.tsx` 의 `DOCS` 목록에 slug 와 제목을 넣는다. `_` 로 시작하는 파일은 뷰어에 나오지 않는다.
- 문서에는 `/` 로 시작하는 앱 내부 링크를 쓸 수 있다(예: `[라이딩 지도](/records/riding-map)`).
